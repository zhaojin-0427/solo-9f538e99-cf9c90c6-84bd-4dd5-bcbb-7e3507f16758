# 旧答卷夜骑纳入核查（Flask）

交通调查员判断**旧版答卷能否纳入新版夜骑分析**的核查页：上传旧答卷的已答筛查项与
当时展示/跳过的全部追问题号，录入旧版各追问题的展示条件与新版纳入条件后，系统自动
判断哪些未答筛查项的补全能与旧档相符，并以**最少的最坏补问题数**推荐电话补问题目。

## 一、判定逻辑

### 条件语言（至多 12 个是非筛查项）

- 变量：字母/下划线开头的标识符，如 `S1`、`X_1`
- 与：`AND` / `&&` / `&` / `与` / `且`
- 或：`OR` / `||` / `|` / `或`
- 非：`NOT` / `!` / `~` / `非`（支持紧贴写法，如 `非S1`、`S1或S2`）
- 括号 `( )` 与常量 `true/false`（也可写 `真/假`、`是/否`、`1/0`）
- 优先级：`非` > `与` > `或`，括号可改变优先级
- 示例：`S1 AND (S2 OR NOT S3)`、`非S1 与 (S2 或 S3)`

### 约束与补全

n 个筛查项共 2^n 种真值组合（n ≤ 12，即最多 4096 种），逐一枚举并过滤：

1. 已答筛查项：补全必须与答案一致；
2. 当时**展示过**的追问题：其展示条件在补全下必须为**真**；
3. 当时**跳过**的追问题：其展示条件在补全下必须为**假**。

过滤后：

- **无可行补全** → 旧档矛盾，页面给出一个极小（每个约束都必不可少的）矛盾核，
  列出需要优先电话核对的记录；
- **可行补全的纳入结论全部一致** → 直接判定“纳入/不纳入”，无需再打电话；
- **结论仍有分歧** → 用 minimax 决策树计算“从当前状态起最坏还要问几题”，
  推荐使该题数最小的未答筛查项；被现有约束唯一确定的未答项会标为“隐含”，无需再问。

每回答一题立即重新判定；若新答案与旧档冲突，拒绝该提交、提示冲突约束，并保留提交前
的结果与全部历史答案。

## 二、数据格式

### 配置（可与答卷合并上传，键为 `config` / `archive`）

```json
{
  "items": ["S1", "S2", "S3"],
  "labels": {"S1": "夜间佩戴头盔", "S2": "配有车前灯", "S3": "单次夜骑超30分钟"},
  "followups": [
    {"qid": "Q1", "condition": "S1 AND NOT S2", "shown": true},
    {"qid": "Q2", "condition": "S3 OR S1", "shown": false}
  ],
  "inclusion": "S1 AND (S2 OR S3)"
}
```

- `shown` 为配置阶段的初值，上传答卷后以答卷记录为准重建。

### 旧答卷

```json
{
  "answers": {"S1": true},
  "followups": [
    {"qid": "Q1", "shown": true},
    {"qid": "Q2", "shown": false}
  ]
}
```

- 必须列出配置中的**全部**追问题号（展示或跳过都要显式记录），缺号会报错，
  避免“没列出”与“明确跳过”产生歧义；
- 兼容只给 `shown_qids`（展示题号数组）的简化形式。

完整示例见 `sample/config_with_archive.json`、`sample/archive_only.json`。

## 三、启动方式

### Docker Compose（推荐）

```bash
SECRET_KEY=$(openssl rand -hex 32) docker compose up --build
# 浏览器打开 http://localhost:8000
```

不设置 `SECRET_KEY` 时使用开发默认值，仅适合本地试用。

### 本地直接运行

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
flask --app 'app.app:create_app' run --debug
```

判定引擎 `app/engine` 仅依赖 Python 标准库，未装 Flask 也可运行演示与引擎测试。

## 四、测试与验证

```bash
# 引擎测试（标准库 unittest，零依赖）
python -m unittest discover -s tests -v

# 无浏览器的全流程 CLI 演示（含跳题判定与冲突补问）
python scripts/demo.py sample/config_with_archive.json

# Web 冒烟（需先启动服务，容器内自带 curl）
BASE=http://127.0.0.1:8000 scripts/smoke_web.sh
```

## 五、目录结构

```
app/
  app.py                 # Flask 路由（配置/答卷上传、补问、冲突保留、重置）
  engine/
    conditions.py        # 布尔条件词法/语法解析、AST 求值
    config.py            # 配置与答卷的数据模型、校验
    solver.py            # 可行性枚举、极小矛盾核、minimax 最坏题数
  templates/ static/     # 核查页
sample/                  # 示例输入
tests/                   # unittest 测试（Flask 缺失时 Web 用例自动跳过）
scripts/                 # CLI 演示与 Web 冒烟脚本
```

## 六、交付核对：已实现 / 已验证 / 遗留项

### 已实现

- 12 个以内是非筛查项，且/或/非（中英文符号）条件解析、括号与优先级；
- 旧答卷已答项 + 全部追问题展示/跳过记录上传，约束所有可行补全；
- 无可行补全时给出极小矛盾核（旧档矛盾提示）；
- 结论一致时直接判定纳入/不纳入；分歧时 minimax 推荐使最坏剩余题数最少的未答项，
  页面显示“从当前起最坏还要问几题”及每个候选题的最坏题数；
- 任一未答项均可填写并重新判定；冲突答案被拒绝、提示并保留提交前结果；
- 隐含确定项提示、答案清空/会话重置、Docker Compose 启动。

### 已验证

- 引擎 21 个 unittest 用例全部通过（解析、优先级、跳题真假约束、矛盾核、
  minimax 题数、12 项上限与重复项校验）；
- 6 个 Flask 路由集成测试通过：在本机无 Flask 的条件下，用一次性的最小 Flask
  兼容垫片（位于仓库外的 `/tmp`，不进入交付物）实跑了真实路由与模板渲染，
  覆盖建立任务、文件上传、分歧推荐、冲突补问被拒且保留提交前结果、矛盾答卷、
  非法 JSON、重复作答、清空答案、会话重置；
- 100 组随机配置与独立穷举参考实现交叉比对，最坏题数与推荐结论零偏差；
- 12 项满配性能：无约束约 76ms、最坏（12 个独立与项）约 0.4s；
- CLI 演示跑通“载入旧档 → 分歧推荐 → 补问后纳入 → 冲突补问被拒”完整链路；
- 边界场景：无追问题、全跳过记录、恒真/恒假条件、无关变量不计入题数。

### 遗留项 / 已知边界

- 本机环境无 pip/Flask/Docker 守护进程，`docker compose up --build` 与
  `scripts/smoke_web.sh` 未能在本机实跑；Dockerfile/compose 已做静态核对，
  Web 逻辑已通过上述垫片等价验证，建议在有 Docker 的环境再执行一次冒烟；
- 会话存于签名 cookie，为单调查员临时核查设计，未做持久化与多用户协作；
- 极小矛盾核返回其中一个极小核（非全局最小基数核）；12 项规模下二者差异
  对电话核对流程无实际影响。
